# 과제 02: 배열과 연결 자료구조를 이용한 이진트리 비교

## [1] 메모리 사용량 측정 및 비교

`hw2_3.c`에서 같은 트리를 배열 방식과 연결 자료구조 방식으로 각각 구성하고 트리 저장에 필요한 메모리를 비교하였다. 일반 이진트리, 완전 이진트리, 오른쪽 편향 이진트리를 한 개씩 사용하였다.

### 측정 방법

배열 방식은 `char tree[10000]`을 사용하며 루트는 1번 인덱스에 저장한다. 인덱스가 `i`인 노드의 왼쪽 자식은 `2i`, 오른쪽 자식은 `2i + 1`에 저장한다. 연결 방식은 문자 데이터와 두 자식 포인터를 가진 `Node`를 노드마다 `malloc`으로 동적 할당한다.

Windows x64에서 C 컴파일러로 실행한 결과 `sizeof(char)`는 1바이트이고 `sizeof(Node)`는 24바이트라 다음 세 값을 구분하여 비교하였다.

- 배열 실제 확보량: `sizeof(tree)`로 구한다. 현재 프로그램에서는 항상 10,000바이트이다.
- 배열 필요 범위: `(최대 사용 인덱스 + 1) × sizeof(char)`로 구한다. 사용하지 않는 0번 칸과 중간의 빈 칸을 포함한다. 현재 프로그램의 실제 할당량이 아닌 같은 인덱스 배치를 유지할 때 필요한 최소 배열 크기이다.
- 연결 노드 할당량: `노드 수 × sizeof(Node)`로 구한다. 각 노드에 요청한 메모리 크기의 합이다.

이 비교는 트리 저장 공간을 대상으로 한다. 구조체 패딩은 `sizeof(Node)`에 포함되지만 `malloc`의 내부 관리 공간, 루트 포인터 변수, 입력 문자열, 재귀 호출 스택 등은 비교에서 제외하였다. `sizeof(Node)`는 실행 환경에 따라 달라질 수 있다.

### 측정 결과

| 트리 종류 | 괄호 표기 | 노드 수 | 최대 사용 인덱스 | 배열 실제 확보량 | 배열 필요 범위 | 연결 노드 할당량 |
|---|---|---:|---:|---:|---:|---:|
| 일반 이진트리 | `A(B(D,),C(,E))` | 5 | 7 | 10,000B | 8B | 120B |
| 완전 이진트리 | `A(B(D,E),C(F,G))` | 7 | 7 | 10,000B | 8B | 168B |
| 오른쪽 편향 이진트리 | `A(,B(,C(,D)))` | 4 | 15 | 10,000B | 16B | 96B |

(포화 이진트리는 완전 이진트리의 조건도 만족하므로 완전 이진트리의 비교 사례로 사용하였다.)

### 결과 분석

일반 이진트리는 배열의 1, 2, 3, 4, 7번 인덱스를 사용한다. 노드는 5개지만 중간에 빈 칸이 있어 0번부터 7번까지 8바이트의 범위가 필요하다. 연결 방식은 5개의 노드를 생성하므로 `5 × 24 = 120`바이트를 할당한다.

완전 이진트리는 배열의 1번부터 7번까지 빈 칸 없이 사용한다. 0번 칸을 포함하여 필요한 범위는 8바이트고 연결 방식은 `7 × 24 = 168`바이트를 할당한다. 배열 크기를 필요한 만큼 정한다면 완전 이진트리는 빈 칸이 거의 없고 자식 포인터도 저장하지 않아 공간을 효율적으로 사용할 수 있다.

오른쪽 편향 이진트리는 배열의 1, 3, 7, 15번 인덱스를 사용한다. 노드가 4개뿐이어도 16바이트의 범위가 필요하다. 연결 방식은 `4 × 24 = 96`바이트를 할당한다. 일반, 완전 이진트리 예제보다 노드 수가 적은데도 배열 필요 범위는 더 크다.

현재 코드의 실제 확보량을 비교하면 세 경우 모두 연결 방식이 더 작다. 배열은 트리 크기에 관계없이 10,000바이트를 확보하지만 연결 방식은 실제 노드 수에 따라 120, 168, 96바이트를 할당하기 때문이다.

반면 필요한 범위만큼 배열을 확보한다고 가정하면 이번의 작은 예제에서는 배열이 세 경우 모두 더 작다. 편향 예제도 배열 필요 범위가 16바이트로 연결 방식의 96바이트보다 작기에 이 수치만으로 편향 트리에서는 연결 방식이 항상 더 작다고 결론 내릴 수는 없다.

편향 트리에서 연결 방식이 유리해지는 이유는 깊이가 증가할 때의 공간 증가량에 있다. 노드가 `n`개인 오른쪽 편향 트리의 마지막 인덱스는 `2^n - 1`이므로 배열 필요 범위는 `2^n`칸으로 증가한다. 연결 방식은 노드 수에 비례해 `n × sizeof(Node)`만큼 증가한다. 따라서 편향이 깊어질수록 배열의 빈 공간이 급격히 늘고 연결 방식이 공간을 더 효율적으로 사용할 수 있다.

이번 예제들은 노드 수가 서로 다르므로 모양만 바꾼 동일 조건 실험은 아니다. 그래도 각 예제의 노드 수, 인덱스, 할당량을 함께 제시하여 실제 구현의 메모리 사용량과 저장 방식의 차이를 비교한 점에서 의미가 있다고 할 수 있다.

## [2] 특정 노드의 자식·부모·형제 조회와 효율 분석

### 프로그램 동작

`hw2_3.c`는 괄호 표기로 입력한 트리를 두 방식으로 구성하고 찾을 노드의 문자를 입력받는다. 각 방식에서 왼쪽 자식, 오른쪽 자식, 부모, 형제를 출력하며, 해당 관계가 없으면 `없음`, 입력한 노드를 찾지 못하면 `노드가 없습니다.`를 출력한다. 노드 이름은 중복되지 않는 영문 대문자 한 글자로 가정한다.

예를 들어 `A(B(D,),C(,E))`를 입력하고 `C`를 찾으면 두 방식 모두 다음 결과를 출력한다.

| 관계 | 결과 |
|---|---|
| 부모 | A |
| 왼쪽 자식 | 없음 |
| 오른쪽 자식 | E |
| 형제 | B |

### 배열 방식

`findArrayNode`는 배열을 순서대로 검사하여 입력한 문자에 해당하는 인덱스를 찾는다. 인덱스 `i`를 찾은 뒤에는 아래 계산으로 관계를 구한다.

- 부모: `i / 2`의 정수 나눗셈 결과. 루트에는 부모가 없다.
- 왼쪽 자식: `2i`
- 오른쪽 자식: `2i + 1`
- 형제: `i`가 짝수이면 `i + 1`, 홀수이면 `i - 1`. 루트에는 형제가 없다.

계산한 위치가 배열 범위 안에 있고 실제 노드가 있는지도 확인한다. 노드의 인덱스를 이미 알고 있다면 각 관계를 구하는 시간은 `O(1)`이다.

현재 프로그램은 인덱스가 아니라 문자를 입력받으므로 인덱스를 찾는 과정이 필요하다. 배열 용량을 `M`이라고 하면 `findArrayNode`는 빈 칸까지 포함하여 최악의 경우 `M - 1`칸을 검사하므로 `O(M)`이다. 현재 `M`은 10,000이다.

### 연결 자료구조 방식

`findLinkedNode`는 루트에서 시작해 입력한 문자를 가진 노드를 찾는다. 찾은 노드의 `left`, `right` 포인터로 자식에 바로 접근하므로 자식 조회는 `O(1)`이다.

현재 `Node`에는 부모 포인터가 없으니 `findParent`가 루트부터 다시 탐색하여 부모를 찾는다. 형제는 부모를 찾은 후 부모의 다른 자식 포인터로 구한다. 노드 수가 `n`개일 때 노드 검색과 부모 검색은 각각 최악 `O(n)`이고 두 탐색을 합해도 전체 시간 복잡도는 `O(n)`이다.

### 효율 비교

아래 표는 현재 구현의 최악 시간 복잡도이다. `M`은 배열 용량, `n`은 실제 노드 수이다.

| 작업 | 배열 방식 | 연결 방식 |
|---|---|---|
| 문자로 대상 노드 찾기 | O(M) | O(n) |
| 대상 위치를 아는 상태에서 자식 조회 | O(1) | O(1) |
| 대상 위치를 아는 상태에서 부모 조회 | O(1) | O(n) |
| 대상 위치를 아는 상태에서 형제 조회 | O(1) | O(n), 부모를 찾은 뒤에는 O(1) |
| 문자 검색부터 모든 관계 출력까지 | O(M) | O(n) |

노드의 위치를 이미 아는 상황에서는 배열 방식이 부모와 형제를 계산으로 바로 구할 수 있어 현재 연결 구현보다 효율적이다. 자식 조회는 두 방식 모두 `O(1)`이다.

하지만 현재 프로그램처럼 문자를 입력받아 검색하는 과정까지 포함하면 배열이 항상 더 빠르다고 할 수 없다. 배열은 빈 칸도 검사하지만 연결 방식은 실제 노드만 탐색하기에 배열 용량에 비해 노드가 적거나 빈 칸이 많은 경우 연결 방식이 유리할 수 있다. 이 비교는 실행 시간을 측정한 결과가 아니라 코드의 탐색 과정과 시간 복잡도를 분석한 결과이다.

연결 노드에 `parent` 포인터를 추가하면 대상 노드를 찾은 뒤 부모와 형제도 `O(1)`에 조회할 수 있다. 대신 노드마다 부모 포인터를 저장하는 공간과 이를 관리하는 작업이 추가된다. 현재 구현은 부모 포인터 없이 두 자식 포인터만 사용한다.

## 편향 이진트리 판정 기준

편향 이진트리는 강의 시간에 주교수님이 말씀하신 대로 모든 연결이 왼쪽이거나 모든 연결이 오른쪽인 트리로 정의하였다. `A(B(C,),)`와 `A(,B(,C))`는 편향 이진트리고 `A(B(,C),)`처럼 중간에 방향이 바뀌는 트리는 편향 이진트리가 아니다. 노드가 하나인 트리는 편향 이진트리로 처리했다.
