# 과제 12: 퀵 정렬의 피벗 선택에 따른 성능 비교

## 실행

`hw12.c`만 컴파일한다. 시드를 생략하면 현재 시각을 사용한다. 동일한 환경과 시드로 데이터 및 비교 횟수를 재현할 수 있다. C 라이브러리의 난수 구현이 바뀌면 결과는 달라질 수 있으며 실행시간은 같은 환경에서도 변동한다.

## 구현 및 실험 기준

크기 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000마다 0~1,000,000의 정수를 생성한다. 중복을 허용하며 각 크기에서 세 방식은 동일한 원본의 복사본을 정렬한다. 각 크기당 무작위 입력 한 개를 사용한다. 데이터 생성 시드를 크기별로 설정하여 무작위 피벗에서 소비한 난수가 다음 크기의 입력 생성에 영향을 주지 않도록 했다.

세 방식은 `choose_pivot`의 선택 부분만 다르고 동일한 Lomuto 분할 함수를 사용한다. 선택한 피벗을 마지막으로 옮긴 뒤 나머지 원소 각각을 피벗과 `<`로 비교한다. 작은 원소는 왼쪽, 같거나 큰 원소는 오른쪽으로 분할하고 피벗을 확정한다.

- First: 현재 구간의 첫 원소.
- Random: 분할할 때마다 현재 구간 안의 새 무작위 위치.
- Median-3: 첫 위치, `lo+(hi-lo)/2`, 마지막 위치의 값 중 중앙값. 산술평균을 사용하지 않는다. 2~3회의 값 비교를 수행하며 동률도 처리한다. 길이 2에서는 첫 위치와 가운데 위치가 같으며 이 경우에도 실제 수행한 비교를 센다.

출력의 총 비교는 `partition + pivot`이다. 분할에서 값과 피벗을 비교할 때마다 결과에 관계없이 1회, 중앙값 결정에서 값끼리 비교할 때마다 1회 센다. 인덱스 검사, 난수 생성, 교환, 복사, 검증은 집계하지 않는다. 라이브러리 `qsort`는 검증용 기준 배열 생성에만 사용한다. 정렬 결과를 기준 배열과 원소별로 대조하여 오름차순과 중복을 포함한 데이터 보존을 모두 검사한다.

## 보너스 측정 방법

재귀형은 왼쪽 부분 구간을 정렬한 후 오른쪽을 정렬한다. 반복형은 명시적인 구간 스택을 사용하며 오른쪽을 먼저 넣고 왼쪽을 나중에 넣어 재귀형과 동일한 처리 순서를 유지한다. 두 구현은 같은 피벗 선택 함수와 분할 함수를 공유한다.

여섯 크기 모두 동일 원본과 Median-of-Three를 사용한다. 각 구현을 한 번 예열한 후 각각 100회 측정해 평균 ms를 출력한다. 반복마다 원본을 다시 복사하며 홀수·짝수 회차에서 실행 순서를 번갈아 적용한다. Windows에서는 고해상도 `QueryPerformanceCounter`를 사용한다. 비 Windows 환경의 대체 타이머는 `clock()`이며 CPU 시간과 해상도 차이가 있으므로 플랫폼을 섞어 비교하지 않는다.

측정 범위는 정렬 함수 호출 직전부터 반환 직후까지다. 데이터 생성, 원본 복사, 기준 정렬, 결과 검증·출력, 반복형 스택 메모리 할당은 제외한다. 실제 스택 넣기·빼기와 함수 호출 및 비교 계수 갱신은 정렬 수행 비용에 포함한다. 반복형에는 최대 n개의 구간을 저장할 공간을 미리 할당한다. 모든 측정에서 정렬 결과와 두 종류의 비교 횟수가 재귀형 기준과 같은지도 확인한다.

### 데이터 크기 증가의 영향

크기가 두 배씩 증가한 구간에서 First 비교는 약 2.30, 2.01, 2.41, 2.06배, Median-3은 약 2.23, 2.24, 2.17, 2.25배로 증가했다. Random 역시 대략 두 배 전후로 증가했다. 무작위 입력에서 비교 횟수가 일반적으로 O(n log n) 규모로 증가하는 경향과 부합하며 이차 증가처럼 매번 약 네 배가 되지는 않았다. 16,000→20,000은 2배가 아닌 1.25배 증가이고 총 비교는 각각 약 1.39, 1.23, 1.23배였다. 각 크기의 입력 및 분할 형태가 다르므로 증가율이 일정하지는 않다.

### 피벗 선택과 분할의 관계

이 구현에서 길이 m인 한 구간의 분할 비교는 항상 m-1회다. 피벗 선택은 당장의 분할 비교 수보다 이후에 정렬할 두 구간의 크기를 바꾼다. 양쪽 크기가 비슷하면 깊이가 작아지고 한쪽으로 치우친 분할이 반복되면 같은 원소들이 더 많은 단계에서 비교된다. 극단적으로 매번 최솟값이나 최댓값을 선택하면 비교 합이 n(n-1)/2가 된다.

First는 피벗 선택을 위한 값 비교가 없다. 무작위 입력의 첫 값이 항상 나쁜 것은 아니므로 이번에는 4,000개와 16,000개에서 총 비교가 가장 적었다. 반면 정렬된 서로 다른 값의 입력에서는 첫 값이 계속 최솟값이 되어 이 분할 방식의 최악 경우가 된다.

Random은 특정 위치에 의존하지 않아 입력 순서가 고정된 패턴일 때의 위험을 줄일 수 있지만 실제로 뽑은 값이 중앙에 가깝다는 보장은 없다. 이번에는 20,000개에서 First보다 21,882회 적게 비교했지만 나머지 다섯 입력에서는 더 많이 비교했다. 이는 한 번의 무작위 선택 결과이며 Random이 일반적으로 더 나쁘다는 결론을 뜻하지 않는다.

Median-3은 세 표본 중 극단값을 제외하여 더 균형 잡힌 분할을 유도한다. 세 표본의 중앙값이 전체 구간의 정확한 중앙값인 것은 아니다. 이번에는 모든 크기에서 분할 비교 자체는 First와 Random보다 적었다. 그러나 중앙값을 찾는 비교도 비용이다. 4,000개에서는 First보다 분할 비교를 2,535회 절약했지만 선택 비교 5,959회가 추가되어 총 3,424회 많았다. 16,000개에서도 11,612회 절약보다 선택 비용 23,900회가 커 총 12,288회 많았다.

20,000개에서는 Median-3이 분할 비교를 First보다 55,543회 절약하고 선택 비용 29,986회를 사용해 총 25,557회, 약 7.44% 적었다. Random과 비교하면 총 3,675회, 약 1.14% 적었다. 따라서 이번 실험에서는 Median-3이 6개 중 4개 크기에서 가장 효과적이었지만 선택 비용 때문에 모든 입력에서 우세하지는 않았다. 크기별 한 입력 및 한 번의 피벗 난수열을 측정했으므로 보편적인 순위로 일반화하지 않는다.

중복은 올바르게 처리하지만 이 이분할 구현은 같은 값을 오른쪽에 모은다. 모두 같은 값이면 세 방식 모두 불균형 분할로 O(n²) 비교가 발생한다. Median-3이나 Random만으로 이 문제를 해결하지는 않는다. 재귀형은 그런 입력에서 호출 깊이도 O(n)이 되어 매우 큰 최악 입력은 실행 환경의 스택 한계에 걸릴 수 있다. 본 실험의 지정된 무작위 입력은 모두 정상 완료했으며 중복만 있는 별도 작은 입력으로 정확성도 검사했다.

두 구현은 모든 측정에서 정렬 결과뿐 아니라 분할 비교와 중앙값 선택 비교도 정확히 같았다. 따라서 이 차이는 피벗이나 분할 품질이 달라져서 생긴 차이가 아니다. 반복형은 재귀 호출을 줄이는 대신 명시적인 구간 스택의 저장·조회 및 반복 제어가 필요하다. 재귀형은 함수 호출 및 호출 스택 관리 비용이 있고, 컴파일러의 최적화도 실제 비용에 영향을 준다.

이번에는 1,000개에서 재귀형이 근소하게 빨랐고 나머지에서 반복형이 빨랐다. 20,000개의 차이는 0.008692ms, 재귀형 대비 약 1.13%였다. 두 구현 모두 동일한 분할 작업이 대부분을 차지하므로 시간은 비슷했다. 작은 차이는 운영체제 스케줄링, 캐시 상태, CPU 주파수 및 측정 변동의 영향도 받을 수 있다. 실행 순서 교대와 100회 평균으로 영향을 줄였지만 분산이나 통계적 유의성을 측정하지 않았으므로 반복형이 항상 빠르다고 결론 내리지는 않는다. 이 측정은 비교 계수를 갱신하는 현재 구현 및 최적화 옵션에 대한 결과다.
